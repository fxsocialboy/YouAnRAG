# 阶段二分阶段开发计划：Qdrant Local 接入与 Markdown 知识库自动更新

## 0. 阶段定位

阶段二的目标是把阶段一已经收口的 `Stage1 FAISS + chunk_metadata` 静态检索能力，升级为基于 **Qdrant Local + SQLite DocumentRegistry** 的轻量可更新向量知识库。

本阶段不以提升语义相关性为第一目标，而是补齐 RAG 项目的工程能力：

1. 使用 Qdrant 管理 chunk 向量和 payload；
2. 支持 payload filter；
3. 支持 chunk upsert/delete；
4. 使用 SQLite 记录文档 hash 和 chunk 映射；
5. 支持 Markdown 新增、修改、删除后的同步；
6. 保持 Stage1 FAISS 产物不被覆盖，确保阶段一可回退。

本阶段默认使用：

```text
Qdrant Local + SQLite
```

代码中保留 Qdrant Server 迁移配置，但阶段二不实现 Docker/Qdrant Server 部署。

## 1. 为什么采纳精简方案

DeepSeek 的建议有道理：当前是单人简历项目，知识库只有 51 份 Markdown，阶段二应该突出“Qdrant 迁移 + 自动更新核心能力”，而不是做生产级同步平台。

因此本版计划做以下收敛：

| 原设计 | 调整后 |
|---|---|
| `documents/chunk_mappings/sync_runs/kv_state` 四张表 | 只保留 `documents/chunk_mappings` 两张表 |
| `scanner.py + change_detector.py` 两个模块 | 合并为 `sync/file_tracker.py` |
| 独立 `SyncService` 服务类 | 第一版同步逻辑直接写在 `sync_qdrant_stage2.py` 脚本中 |
| 8 个小阶段 | 压缩为 6 个小阶段 |
| 阶段二评测看 Recall 提升 | 改为看 Stage1 与 Qdrant 检索一致性 |

保留不变的部分：

- `VectorStore Protocol`；
- `QdrantStore`；
- 从 FAISS `reconstruct()` 复用向量；
- Qdrant payload 字段设计；
- 不修改 Stage1 artifacts；
- 文档级重建策略；
- 整体后续路线：Qdrant → BM25 → rerank → query rewrite。

## 2. 收敛原则

1. **不修改阶段一 artifacts**：


2. **阶段二所有新产物写入**：

3. **不重新全量 embedding**：第一版从 Stage1 FAISS `reconstruct` 向量导入 Qdrant，本地 CPU 可完成；

5. **少量新增/修改文档可 CPU embedding**；如果要全量重建 51 份文档 embedding，需要提前租 GPU；
6. **每个小阶段完成后跑单元测试**；
7. **每个小阶段都要能独立收敛，不影响 Stage1 searcher 正常运行**。

### 开发内容

```powershell

```

第一版不做独立 `SyncService` 类，同步逻辑直接在脚本中收敛。

处理策略：

| 变化 | 操作 |
|---|---|
| unchanged | 跳过 |
| added | 解析、分块、embedding、upsert、写 registry |
| modified | 删除该文件旧 points，重建该文件 chunks |
| deleted | 删除该文件 points，Registry 标记 deleted |

### GPU 提醒

- `--scan-only` 不需要 GPU；
- 从 Stage1 导入 Qdrant 不需要 GPU；
- 少量 added/modified 文档可以 CPU；
- `--rebuild-all` 如果重新 embedding 51 份文档，建议提前租 GPU。
