# 阶段四分阶段开发计划：Cross-Encoder 精排与 MMR 多样性控制（修订版）

## 0. 阶段定位

阶段四建立在前三阶段已收口成果之上：

```text
Stage1：Markdown 解析 + token chunk + BGE embedding + FAISS 基线
Stage2：Qdrant Local + SQLite Registry + Markdown 文档级同步
Stage3：Qdrant dense + 本地 BM25 sparse + RRF 融合 + metadata filter + context packing
```

阶段三的 `HybridSearcher` 本质是**粗排召回**：dense 和 sparse 各自召回候选，再用 RRF 融合排名。它已经能提升召回覆盖，但仍有两个问题：

1. **精度不足**：Bi-encoder 独立编码 query 和 passage，无法对 `(query, passage)` 做细粒度交互判断；RRF 只使用排名，不直接判断候选与 query 的语义相关性。
2. **证据同质化**：相邻 chunk、同一来源或同一章节可能占据过多 Top-K，影响最终 evidence 的覆盖面。

阶段四目标：在阶段三粗排结果之后增加：

```text
Cross-Encoder rerank：提高候选相关性排序
MMR diversity selection：控制最终候选同质化
Stage4 evaluation：用 MRR@10、rank_shift、recall 和 latency 证明收益
```

阶段四完成后的链路：

```text
query
→ metadata filter
→ dense recall(Qdrant)
→ sparse recall(BM25)
→ RRF fusion（粗排候选）
→ Cross-Encoder rerank（精排）
→ MMR diversity selection（多样性选择）
→ ContextPacker（邻接 chunk / 同 section 补全 / token budget / citation）
→ structured evidence output
```

## 1. 对原计划的评审结论

原计划整体方向是合理的：阶段四确实应该做 Cross-Encoder rerank 和 MMR，并且应保持阶段三入口不变、新增 Stage4 独立入口。

但原计划有几处需要修正：

### 1.1 `ContextPacker` 完全零改动不合理

当前 `ContextPacker` 内部会按 `fusion_score` 重新排序。如果 Stage4 rerank / MMR 只改变候选顺序，但 `ContextPacker` 仍只看 `fusion_score`，那么最终 evidence pack 的顺序可能退回阶段三粗排顺序，导致 rerank/MMR 对最终上下文影响不充分。

修正：允许对 `ContextPacker` 做**向后兼容的小改动**：

- 默认行为保持 Stage3 不变；
- 新增可选排序字段或自动优先级：

```text
mmr_score > rerank_score > fusion_score
```

这样 Stage3 不受影响，Stage4 的精排/多样性结果能真正进入最终 evidence。

### 1.2 Reranker 默认开启风险偏高

如果在全局 config 中默认 `enable_reranker=True`，后续某个入口误用 `from_config()` 可能触发模型下载或慢推理。

修正：

- 全局配置默认关闭：`enable_reranker=False`、`enable_mmr=False`；
- Stage4 CLI 默认开启 rerank/MMR，但提供 `--no-rerank`、`--no-mmr`；
- 单测和无模型环境使用 `FakeReranker` 或 `--fake-reranker` 跑通。

### 1.3 `RerankResult` 返回类型描述不一致

原计划同时说 `rerank()` 返回 `list[RerankResult]`，又说输出仍是 `list[HybridSearchResult]`。为了管线最简单，阶段四应统一为：

```text
BaseReranker.rerank(query, candidates) -> list[HybridSearchResult]
```

`RerankResult` 可不做，或者只作为内部 trace 数据结构。第一版不需要单独引入。

### 1.4 MMR relevance 必须归一化

`rerank_score`、`fusion_score`、BM25 分数、dense 分数不在同一量纲。MMR 使用 relevance 时必须先归一化，否则 `λ` 的含义不稳定。

修正：

- MMR 内部对 relevance 做 min-max normalization；
- 全相等时统一置为 1.0；
- `mmr_score` 写入的是归一化后的 MMR 目标函数值。

### 1.5 真模型评测需要提前提醒 GPU / 服务器

阶段四单测、本地 fake 流程不需要 GPU；真实 `bge-reranker-base` 批量评测建议在 GPU 服务器跑。后续开发中凡是需要真实 reranker 批量评测，必须先提醒用户再执行。

## 6. 小阶段 4.2：Cross-Encoder Reranker 实现

### 目标

实现 reranker 模块，先用 fake reranker 保证本地可测，再保留真实模型接入。

### 开发内容

新增：

```text
G:\tiaozhanbei\newrag\src\rag_v2\retrieval\reranker.py
```

核心类：

```python
class BaseReranker(Protocol):
    def rerank(self, query: str, candidates: list[HybridSearchResult]) -> list[HybridSearchResult]: ...
```

实现：

1. `FakeReranker`
   - 用于单测和无模型流程；
   - 支持传入 `chunk_id -> score`；
   - 写入 `rerank_score`，按分数降序更新 `rank`。

2. `CrossEncoderReranker`
   - 懒加载 `sentence_transformers.CrossEncoder`；
   - 构造 `(query, content)` pairs；
   - `predict()` 得到 rerank score；
   - 写入 `rerank_score`，按分数降序更新 `rank`；
   - 异常时返回原 candidates，不阻断主流程。

第一版不做强 timeout 中断。原因：Python 线程中强杀模型推理不稳，容易引入复杂度。阶段四先做异常 fallback，真实 timeout 可以在后续服务化阶段通过进程级隔离或推理服务实现。

### 学习建议

建议重点读：

```text
G:\tiaozhanbei\newrag\src\rag_v2\retrieval\reranker.py
```

面试高频问题：

> Cross-Encoder 和 Bi-Encoder 的区别是什么？为什么 rerank 只用于 Top-30 候选？

回答要点：

- Bi-Encoder：query 和 passage 独立编码，适合大规模召回，速度快；
- Cross-Encoder：query 和 passage 拼接后联合编码，交互更充分，排序更准，但成本高；
- 所以工程上先粗召回，再对少量候选精排。

## 7. 小阶段 4.3：MMR 多样性选择

### 目标

实现 MMR，避免 rerank 后同来源、同章节、近重复 chunk 占满最终候选。

### 开发内容

新增：

```text
G:\tiaozhanbei\newrag\src\rag_v2\retrieval\mmr.py
```

核心设计：

```python
class PassageEmbedder(Protocol):
    def encode_passages(self, passages: list[str]) -> np.ndarray: ...

class MMRSelector:
    def select(self, candidates: list[HybridSearchResult], top_k: int) -> list[HybridSearchResult]: ...
```

MMR 计算：

```text
MMR(i) = λ * relevance(i) - (1 - λ) * max_sim(i, selected)
```

实现细节：

1. relevance 优先级：

```text
rerank_score > fusion_score
```

2. relevance 做 min-max normalization；
3. passage embedding 使用 BGE `encode_passages()`，单测用 fake embedder；
4. 相似度使用归一化向量点积；
5. 写入 `mmr_score`，更新 `rank` 和 `stage4_rank`。

### 单元测试

新增：

```text
G:\tiaozhanbei\newrag\tests\test_mmr.py
```

测试点：

- 相似 chunk 会被惩罚；
- 正交 chunk 更容易被选中；
- `lambda=1` 退化为纯 relevance；
- `lambda=0` 偏向多样性；
- `top_k=0/1/超过候选数`；
- 单测不加载真实 BGE。

### 验收标准

- 全量单测通过；
- MMR 不侵入 QdrantStore；
- 不重建全量 embedding。

### 学习建议

建议读：

```text

```

面试可讲：MMR 用一个可调参数 `λ` 在相关性和多样性之间折中，适合解决 Top-K 结果高度重复的问题。

## 13. 风险与缓解

| 风险 | 缓解 |
|---|---|
| reranker 模型下载失败 | 先用 `FakeReranker` 开发和测试；真实模型单独下载到 `models/bge-reranker-base` |
| 本地 CPU 真实 rerank 慢 | 真模型批量评测前提醒用户租 GPU；本地只跑 fake 或少量 smoke |
| rerank 改了候选但 packer 仍按 fusion 排 | 阶段 4.4 对 `ContextPacker` 做向后兼容排序扩展 |
| MMR 相关性分数量纲不一致 | MMR 内部做 min-max normalization |
| MMR 降低 doc_recall | 报告同时看 recall、MRR、rank_shift；必要时调高 `mmr_lambda` 或减小 MMR 强度 |
| Stage4 破坏 Stage3 可复现 | Stage3 CLI/evaluate 不改；每阶段跑全量回归 |

## 14. 阶段四面试表述建议

> 在 dense+sparse 混合召回的 RRF 粗排结果上，我进一步接入 Cross-Encoder reranker 对 query-passage pair 做联合建模精排，并在最终证据选择前加入 MMR 多样性控制。工程上我把 rerank_score、mmr_score 和原 fusion_score 放在统一结果结构里流转，同时保留开关和异常降级；评测上用 MRR@10 和 rank_shift 证明 reranker 是否把相关 chunk 前移，用 recall 和 latency 评估收益与代价。为了不破坏已有阶段，我保留 Stage3 入口不变，Stage4 通过独立 pipeline 和 CLI 接入。
