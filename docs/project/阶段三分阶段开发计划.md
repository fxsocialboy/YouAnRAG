# 阶段三分阶段开发计划：混合召回与上下文组装

## 0. 阶段定位

阶段三的目标，是在阶段二已经收口的：

```text
Qdrant dense retrieval + SQLite Registry + Markdown sync
```

基础上，进一步把检索能力从“能查到相似 chunk”，升级为“能给 Agent / LLM 提供更完整、更可解释证据”的检索管线。

本阶段重点不是继续做数据库基础设施，而是补齐两类能力：

1. **混合召回**：dense 语义匹配 + sparse 关键词匹配；
2. **上下文组装**：把零散 Top-K chunk 变成可直接送进 LLM 的 evidence pack。

阶段三完成后，RAG 检索链路应演进为：

```text
query
→ dense recall
→ sparse recall
→ RRF fusion
→ soft/hard metadata filter
→ context packing
→ structured evidence output
```

## 4. 小阶段 3.1：BM25 本地索引与 sparse 检索

### 目标

先补齐 sparse 召回，让项目具备关键词、数字、条款、文件名相关问题的精确匹配能力。

### 开发内容

新增：

```text

G:\tiaozhanbei\newrag\scripts\build_bm25_stage3.py
```

第一版 BM25 直接基于：

```text
G:\tiaozhanbei\newrag\artifacts\stage1\chunk_metadata.json
```

构建本地轻量稀疏索引。

BM25 实现方式已经固定为：

```text
自己手写
```

也就是：

- 不依赖第三方 BM25 包；
- 自己实现 term frequency；
- 自己实现 document frequency；

- term frequency / document frequency；
- BM25 打分；
- Top-K sparse search；
- 返回 `chunk_id/source_file/chunk_index/section_path_text/content_preview`。

第一版不要求：

- Elasticsearch；
- 倒排索引数据库化；

## 6. 小阶段 3.3：Metadata 软过滤 / 硬过滤

### 目标

让检索在“指定地区、指定文件、指定灾种”场景下更可控，但又避免错误过滤导致零召回。

### 开发内容

新增：

```text
G:\tiaozhanbei\newrag\src\rag_v2\retrieval\filters.py
```

第一版**实际启用**只做：

- `source_file`

第一版**代码预留但不激活**：

```text
地域
灾种
文档类型
```

也就是说，`filters.py` 中保留 hook / Reserved Fields 接口，但阶段三第一版不把这些字段作为真实过滤条件。

当前收敛策略：

```text
明确指定 source_file / 文档名 -> 硬过滤
地域 / 灾种 / 文档类型         -> 保留扩展接口，不实际激活
```

原因很直接：

- 当前 chunk payload 中没有稳定的地域 / 灾种 / 文档类型字段；
- 只靠 query 中正则猜测，误判风险较高；
- 这类 filter 更适合后续结合 metadata 标注后再激活。

### 单元测试

新增：

```text
G:\tiaozhanbei\newrag\tests\test_filters.py
```

测试：

- 明确文件名时触发硬过滤；
- Reserved Fields hook 可正常保留；
- 未识别 metadata 时不报错；
- 第一版不会误触发非 `source_file` 硬过滤。

### 验收标准

- `source_file` 指定检索可控；
- 地域 / 灾种 / 文档类型不错误激活；
- 过滤逻辑独立于 BM25 / dense 搜索层。

### 学习建议

这个阶段代码建议你**知道设计即可，不必逐行细读**。

原因：

- 面试可能会问“有没有做 metadata filter”；
- 但不太会追着你问每个规则实现细节。

## 7. 小阶段 3.4：上下文组装与 token budget

### 目标

把 fused candidate list 变成可直接供 LLM 使用的 evidence pack。

### 开发内容

新增：

```text
G:\tiaozhanbei\newrag\src\rag_v2\retrieval\context_packer.py
```

第一版上下文组装策略：

```text
候选 chunk
→ 按 source_file + chunk_index 排序
→ 合并相邻 chunk
→ 同 section 限量补 1~2 个 chunk
→ 去重
→ token budget 裁剪
→ 分配 [S1] [S2] 证据引用 ID
→ 输出 structured evidence pack
```

其中“补邻居 chunk”的实现路径，需要在开发中明确二选一：

1. 通过 Qdrant payload filter，按 `source_file + chunk_index` 查询邻接 chunk；
2. 在 `context_packer.py` 内部基于 `chunk_metadata.json` 构建：

```text
source_file -> chunk_index -> chunk metadata
```

的小索引，再做邻居补全。

当前更推荐第二种：

- 实现更简单；
- 不额外增加 Qdrant 查询次数；
- 更适合本地单机项目；
- 更利于你在面试中讲清楚“上下文补全逻辑是怎么做的”。

因此阶段三计划默认采用：

```text
context_packer 内部小索引
```

来完成相邻 chunk 和同 section 限量补充。

要求输出至少包含：

- `source_file`
- `section_path_text`
- `chunk_id`
- `content`
- `citation_id`
- `fusion_score`
- `insufficient_evidence`

### 单元测试

新增：

```text
G:\tiaozhanbei\newrag\tests\test_context_packer.py
```

测试：

- 相邻 chunk 可合并；
- 同 section 补充可用；
- 重复 chunk 被去掉；
- token budget 生效；
- 引用 ID 分配稳定；
- 证据不足时能返回标志位。

### 验收标准

- context pack 可直接供后续 agent / LLM 使用；
- 上下文不超预算；
- 输出保留来源和引用 ID；
- 第一版不需要 GPU。

### 学习建议

重点读：

```text
src/rag_v2/retrieval/context_packer.py
```

因为阶段三真正“像 RAG 工程”的部分，很多时候不是检索本身，而是上下文怎么交给 LLM。
