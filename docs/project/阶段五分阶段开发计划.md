# 阶段五分阶段开发计划：Query Analyzer / Query Rewrite / Multi-Query / 条件 HyDE

## 0. 阶段定位

阶段五建立在阶段四已经收口的检索链路上：

```text
Stage1：Markdown 结构化解析 + token chunk + BGE embedding + FAISS 基线
Stage2：Qdrant Local + SQLite Registry + Markdown 自动同步
Stage3：Qdrant dense + BM25 sparse + RRF + metadata filter + ContextPacker
Stage4：Cross-Encoder rerank + MMR + 四路消融评测
```

阶段五要新增的是 **Query Planning 层**，即在真正检索前先分析用户 query，决定是否需要规范化、扩展、多 query 召回、HyDE 召回以及是否启用 rerank/MMR。

本阶段不重新构建 chunk，不重建 Qdrant，不修改阶段一到阶段四的默认入口。所有新能力通过 Stage5 独立模块和 CLI 接入。

---

## 1. 为什么阶段五要做，但不能做重

阶段四评测得出一个重要结论：

- 自然语言 query 中，rerank 对文档级排序有提升；
- 关键词/条款 query 中，BM25/RRF 更稳定，rerank 可能打乱精确匹配。

所以阶段五的重点不是盲目加 HyDE，而是：

```text
先识别 query 类型
→ 再选择检索策略
→ 对短查询/场景查询补召回
→ 对精确查询保守处理
```

这样面试时可以讲出更完整的优化闭环：

> 我不是简单堆叠算法，而是通过评测发现不同 query 类型适合不同检索策略，因此设计 Query Analyzer 做自适应检索路由。

---

## 2. 总体原则

1. **收敛性优先**
   - 每个小阶段都能独立通过单元测试；
   - 新增代码默认不影响 `search_rerank_stage4.py`、`evaluate_stage4.py`；
   - 阶段五入口失败时必须退回 Stage4 raw pipeline。

2. **先规则，后 LLM**
   - 第一版先实现规则 Query Analyzer / Rewrite；
   - HyDE 先做接口和 fake/stub，不默认接真实 LLM；
   - 但阶段五保留 `--hyde-mode deepseek` 可选真实 HyDE；
   - DeepSeek API Key 通过环境变量 `DEEPSEEK_API_KEY` 读取，不硬编码到仓库。

3. **原查询必须保留**
   - raw query 永远作为第一分支；
   - rewrite/multi-query/HyDE 只做补充召回，不替换原查询。

4. **精确查询防退化**
   - 文件名、条款号、年份、响应等级、明确数字类 query 不做激进改写；
   - 默认不开 HyDE；
   - 可以降低或关闭 rerank。

5. **成本可控**
   - 默认最多 3 个 query branch；
   - HyDE 默认 disabled；
   - 后续如果接真实 LLM，需要 timeout/cache/fallback。

---

## 3. 阶段五最终链路

```text
user query
→ QueryAnalyzer
→ QueryPlan
→ QueryRewriter 生成 branches
    ├─ raw
    ├─ normalized
    ├─ expanded / scenario
    └─ hyde(optional, dense only)
→ 多分支调用 Stage4 pipeline 或 hybrid searcher
→ Branch-aware RRF 合并重复 chunk
→ 可选 rerank / MMR
→ ContextPacker
→ structured output + query_plan + branch trace
```

#### 主要功能

### 5.4 条件 HyDE 接口、Rule 模式与 DeepSeek 适配器

#### 目标

实现 HyDE 的三层模式：默认 disabled，纯本地 rule，可选 deepseek。真实 DeepSeek HyDE 不默认开启，但代码能力要保留。

#### 新增/修改代码

建议新增：

```text

G:\tiaozhanbei\newrag\tests\test_hyde.py
```

必要时修改：

```text
G:\tiaozhanbei\newrag\src\rag_v2\config.py
G:\tiaozhanbei\newrag\src\rag_v2\retrieval\multi_query_pipeline.py
```

#### 主要功能

- 定义 `HydeGenerator` Protocol；
- 实现 `DisabledHydeGenerator`，默认不生成 HyDE；
- 实现 `RuleBasedHydeGenerator`，用模板生成“检索用假设文档”，不作为证据；
- 实现 `FakeHydeGenerator`，供单测和 smoke 使用；
- 实现 `DeepSeekHydeGenerator`，从环境变量 `DEEPSEEK_API_KEY` 读取密钥，调用 DeepSeek API；
- `HydeDocument` 记录：
  - `query`；
  - `content`；
  - `used`；
  - `reason`；
  - `latency_ms`；
  - `mode`；
- HyDE branch 只进入 dense 检索，不进入 BM25，不进入 citation。

DeepSeek 适配器要求：

```text
API: https://api.deepseek.com/v1/chat/completions
model: deepseek-chat
timeout: 8s
retry: 1
key: DEEPSEEK_API_KEY 环境变量
```

Prompt 模板：

```text
你是一个应急管理政策专家。请根据以下用户问题，生成一段简短的检索用假设文档（80~150 字），帮助向量检索引擎找到相关政策段落。只输出文档内容，不要任何前缀、后缀或解释。

用户问题：{query}
```

#### 单元测试

- 默认 disabled 不生成 HyDE；
- `--hyde-mode rule` 可生成本地模板 HyDE；
- `--hyde-mode deepseek` 在未设置 `DEEPSEEK_API_KEY` 时友好报错；
- DeepSeek 请求失败时按配置降级到 rule 或跳过；
- scenario query 可生成 HyDE；
- exact query 不生成 HyDE；
- packed context 中不能出现 HyDE 内容。

#### 收敛标准

- 开发和单测不需要真实 LLM API；
- 不需要 GPU；
- 全量测试通过。

#### 建议阅读

建议读接口设计，不必深读 fake 实现。面试可能问“HyDE 如何避免幻觉污染证据”。

## 5. 是否需要 GPU / AutoDL

阶段五开发本身大部分不需要 GPU：

- QueryAnalyzer：不需要；
- QueryRewriter：不需要；
- MultiQuery pipeline 单测：不需要；
- FakeHyDE / RuleBasedHyDE：不需要；
- fake 评测：不需要。

但以下情况需要提前提醒用户去 AutoDL：

1. 运行真实 `bge-reranker-base` 全量评测；
2. 运行真实 BGE dense 检索的大规模评测且本地 CPU 太慢；
3. 接入本地大语言模型生成 HyDE。

第一版阶段五建议先本地完成代码和 fake/轻量评测；如最后需要真实指标，再去 AutoDL 跑一次。
